§0规范状态与阅读指引#

本文件是 AI Software Factory 的唯一架构宪法。它规定工厂如何组织知识、如何调度智能体、如何约束运行时，以及一个项目要"符合 ASFAS"必须满足什么。它不描述任何具体业务系统。

Part I

Vision · 设计理念

回答一个问题：为什么 AI 时代的软件开发必须重新设计组织方式，而不只是换一个更聪明的代码补全。

Chapter 1导言#

1.1 当前 AI 编码框架的共同结构

把主流 AI 编码框架的架构图叠在一起，会看到同一个形状：一个足够强的模型，加一圈工具，加一点编排。差异集中在编排模式（单 agent / ReAct / Supervisor / swarm）与工具面丰富度上。它们隐含同一个假设：

只要模型够强、工具够多、编排够巧，软件就能被生产出来。

这个假设在单次任务尺度上成立，在长周期多人多智能体尺度上不成立。原因不在模型能力，在于一个被系统性忽略的输入：智能体读到的"项目是什么样"这件事，本身没有被工程化。

1.2 被忽略的输入：项目事实

人类工程师进入一个陌生代码库时，会花几天时间重建一套心智模型：有哪些表、状态怎么流转、哪些约束不能破、为什么当初选了这个方案。这套模型存在人脑里，靠 code review、走廊对话、"上次那个坑"来同步。

智能体没有走廊。它每次会话都从零开始，靠三种渠道重建同一套模型：

渠道可靠性失效方式
读代码准确但不完整代码写了"是什么"，没写"为什么"与"不许怎样"。看到 if (perm && !has) 无法判断这是 fail-open bug 还是有意设计
读文档完整但可能失真文档与代码分叉后，智能体读到的是假事实，并基于假事实继续写代码
模型先验流畅但无关用通用最佳实践填补项目特有约束的空白，产出"看起来对"的代码

三种渠道里，第二种最危险。代码不完整会让智能体停下来问；模型先验产出的东西通常在 review 时能被认出来；而失真的文档会让智能体自信地做错事，且错误随迭代放大。长周期无人值守时这一点是致命的——没有人在中途发现"文档过时了"。

1.3 本规范的命题

FR-2ASFAS 兼容实现MUST把"项目事实"作为一等工程产物对待：它有 schema、有校验器、有 CI 闸门、有 owner、有版本，与代码同等严格。MUST NOT依赖人工 review 来保证文档与代码一致。

这不是"把文档写好"的号召。写好的文档三个月后照样会过时——这是熵，不是态度问题。本规范的做法是让文档不可能过时：文档里的结构化片段是解析目标，与代码侧的闭集做集合相等对拍，校验器挂进测试命令，破坏格式 = 测试红。

这套做法在两个真实仓库上跑通了（附录 G）。它产生的效果不是"文档更整齐"，而是文档开始主动报错——这是本规范全部论证的经验基础。

Evidence · 文档开始报错

在参考实现 GMPGCPwork 中，作者手写完第一版 DOMAIN.md 后运行校验器，立刻被报出漏登记了两张表。人写文档必然漏，这正是对拍不能靠人工 review 的直接证据。同一批校验器还查出了一处存在约两年、无人发现的环境变量登记盲区——不是因为检查逻辑不严，而是因为检查器的扫描面漏了一个目录。见 §25.4。

1.4 与"AI Coding Framework"的定位差异

差别不在多了几个方框，在于事实来源的位置。上图中 Agent 从链条的起点移到了中段：它不再是知识的产生者，而是知识的执行者。这条位移是本规范全部设计决策的源头，展开见 §5。

Chapter 2问题陈述#

本章列出本规范要解决的六个具体故障模式。每个都不是假想的——都能在真实仓库里指出实例。规范后文的每条约束都对应回这里的某一条。

2.1 PS-1 · 上下文不一致（Context Divergence）

多个智能体（或同一智能体的多次会话）对同一个概念持有不同版本的理解。典型触发：A 会话改了 schema，B 会话读的是改前的文档。

为什么这是头号问题：多智能体系统在生产中失败，最常见的原因不是编排模式选错，而是各 agent 之间的上下文不一致。编排模式错了，表现是效率低；上下文不一致，表现是产出正确形式的错误代码——它能通过类型检查，能通过测试（如果测试也基于同一份错误理解），只在运行时或合规审查时暴露。

本规范的对策：§15 元语单一事实来源 + §25 机器对拍 + §39 带版本的语义引用（semantic_refs）。

2.2 PS-2 · 静默漂移（Silent Drift）

文档与代码分叉，且没有任何机制报错。分叉在发生时是无害的（一次小改动忘了同步），累积到某个阈值后变成"文档不可信"，团队于是绕过文档直接读代码——文档正式死亡。

Evidence · 漂移的三种真实形态

参考实现中查获的三类：① 数字漂移——文档自述"共 27 项决策"，实际 33 项；文档称"19 个模块"，实际 21 个。结论是 写数字的文档注定漂移，改为不写数字、以 ls 为准。② 登记漂移——枚举值加了但文档没加。③ 覆盖漂移——检查器存在但扫描面漏了一个目录，导致某个环境变量约两年未被登记。三者在 §25 分别有对策。

2.3 PS-3 · 假绿（False Green）

闸门显示通过，但它实际上什么也没检查。这比没有闸门更危险，因为它让人停止怀疑。

假绿类型成因真实实例
语义假绿检查器的语义模型比被检对象粗把状态机的 impl 标注当作转移级语义，于是同一目标态被同时声明"已实现"和"未实现"却都判通过。改为状态级语义并显式检测矛盾声明后才真正生效
时点假绿检查"已提交的历史"而非"即将提交的内容"用 git log --diff-filter 与 git grep 做守护，两者都看不到工作区未提交的改动——而那恰恰是闸门最该拦的时刻。改用 git diff HEAD + 直接读磁盘
覆盖假绿扫描面不完整见 PS-2 的第三类
豁免假绿测试被 skip/only 而套件仍显示绿对不变量测试加 skip 被列为不设放行路径的禁令（§27）

FR-3每个校验器MUST随附负向验证：构造一个应当失败的输入，确认它确实失败，再回滚确认恢复通过。未经负向验证的校验器MUST NOT计入一致性证据。

2.4 PS-4 · 无法归属（Unattributable Change）

面对一处可疑代码，无法回答：谁改的、依据什么决策、谁放行的、当时跑过哪些闸门。对普通项目这是效率问题；对受监管系统这是合规缺陷——检查官可以直接问"这段签名逻辑是谁写的、依据什么、谁审的"。

本规范的对策：§27 决策血缘（append-only、ALCOA+ 对齐）。

2.5 PS-5 · 越权与不可逆损坏

智能体执行了一个即使人类批准也不应执行的动作：改已应用的数据库迁移、削弱审计不可删守护、把密钥写进入库文件。这类动作的共同特征是损坏的是证据本身，事后无法通过再改一次来修复。

本规范的对策：§27 动作分级 L0–L3，其中 L3 不设人工放行路径——判据是"即使有人批准，这个动作本身仍然违规或造成不可逆的证据损坏"。

2.6 PS-6 · 确定性约束被模型化

把本可以用确定性规则表达的检查，做成了"让一个 agent 去审查"。这看起来更智能，实际上是用不可验证约束替换了可验证约束，同时丢掉可复现性。

FINV-1能用确定性规则表达的约束，MUST NOT交给模型执行。这条是不变量而非建议：违反它会使整个一致性体系失去可验证基础。清单与判据见 §34。

Chapter 3设计目标#

六条目标。每条配一个可核查问题——不能被核查的目标是口号，本规范不收。

FG-1Agent Native　工厂的一切产物MUST首先对智能体可读、可解析、可验证，其次才考虑对人的观感。当二者冲突时，机器可解析性优先。

核查问题：随便挑一份工厂文档，能否写出一个 20 行以内的解析器提取其规范性内容？如果需要自然语言理解才能提取，则不满足。

FG-2Knowledge First　知识MUST先于智能体存在。项目在没有任何编排面的情况下，元语层MUST独立成立并独立产生价值。

核查问题：如果永远不上多智能体，这套元语还值得做吗？答案必须是"值得"。§14 FINV-4 把它变成硬顺序约束。

FG-3Event Driven　工作流的推进MUST由显式事件触发，MUST NOT依赖智能体"自己觉得该做下一步了"。事件MUST可持久化、可重放。

核查问题：杀掉编排进程再重启，工作流能否从最后一个事件恢复而不重做已完成的活动？

FG-4Project Independent　工厂MUST NOT包含任何单一项目的业务知识。工厂与项目之间只有一条接口：元语契约。

核查问题：在工厂代码库中 grep 任一项目的业务术语，命中数MUST为 0（测试夹具除外）。

FG-5Runtime Replaceable　运行时MUST可替换。工厂层MUST NOT直接依赖任何厂商 SDK 的类型或调用；一切经 §35 的运行时抽象接口。

核查问题：在工厂层 grep 厂商 SDK 的 import，命中MUST仅出现在 runtime/<vendor>/ 适配器目录内。

FG-6Governed by Default　治理能力MUST与自主性能力同步交付，MUST NOT后置。新增一档自主性之前，对应的动作分级、血缘字段与护栏MUST已在册。

核查问题：能力注册表中是否存在已实现但未登记的角色？MUST为 0。

关于 Cloud Native

原方案稿列有 Cloud Native 目标。本规范不将其列为设计目标，降级为 §48 的基础设施选型约束。理由：云原生描述的是部署形态，不是本体系的区分性特征——一个跑在单机上的工厂只要满足 FG-1–FG-6 仍然符合 ASFAS。把部署形态写进设计目标会让目标层与实现层混淆，且诱导预埋（§4 FP-6）。

Chapter 4设计原则#

目标说"要达到什么"，原则说"遇到分歧时按什么判"。每条原则MUST能落到 grep / 约定测试 / CI 门禁三选一——写不出守护方式的原则会被删。

FP-1Single Source of Truth　每个事实MUST只有一处权威定义。其他位置MUST用引用，MUST NOT复制。复制即制造第二个事实来源，而两个事实来源必然在某天分叉。

守护：链接可解析性校验 + 集合相等对拍（§25）。推论：论证留在出处文档，登记册只放"ID + 一句话 + 结论 + 出处"（§21）。本规范自身遵守此条——它不复制任何参考实现的表格内容（§6.4）。

FP-2Everything is Reviewable　任何影响产物的决定MUST留下可审查痕迹：决策入登记册，改动入血缘，放行入闸门记录。MUST NOT存在"只有当时那个会话知道为什么"的改动。

守护：血缘字段完整性校验；触及高影响路径面的改动无放行记录 = 红。

FP-3Everything is Replaceable — except Knowledge　运行时、模型、编排模式、云厂商MUST可替换。唯独元语层不可替换——它是工厂的核心资产，其余都是可换的实现。

守护：FG-5 的 import 边界测试。推论：换 Runtime 时元语零改动，是 §40 替换协议的验收条件。

FP-4Fail Closed　守卫解析不出结论时MUST拒绝，MUST NOT放行。校验器遇到无法解析的输入MUST报错，MUST NOT跳过。

Evidence · 一个字符的 fail-open

参考实现中一处权限守卫从 if (!perm || !perms.has(perm)) throw FORBIDDEN 被改为 if (perm && !perms.has(perm)) throw FORBIDDEN。校验顺序完全没变，判据却从"解析不出权限就拒绝"翻转为"解析不出就放行"——任何将来漏映射的动作都会静默跳过鉴权。"顺序看着对"不等于"判据是对的"。 由此得出 FP-4 的操作化推论：合规路径上的守卫，MUST逐条阅读判据的否定分支。

FP-5Diagnose, Never Auto-Fix　治理工具MUST NOT提供 --fix。校验器只报告违规与位置，修复由人或智能体在理解原因后进行。

理由：自动修会让执行者跳过"为什么违规"，把治理降级成格式化器。而违规的价值恰恰在于它揭示了理解偏差。守护：传入 --fix MUST以非零码退出。

FP-6No Speculative Scaffolding　MUST NOT预埋"以后可能用到"的代码、配置或注册项。能力注册表MUST是闭集：没有编排面就不登记编排角色。

理由：预埋的注册项无法被负向验证（它指向不存在的东西），会成为下一轮假绿的温床。守护：注册表条目的路径面 glob MUST能匹配到真实存在的路径。

FP-7Honest Gaps　无法机器化守护的约束MUST显式登记为"仅文档约束"并说明原因，MUST NOT省略不提，也MUST NOT假装已被守住。

理由：登记一条挡不住的禁令，比假装它被挡住要好——读者由此知道该靠人盯，而不是误以为有闸门。这条把"诚实"从美德变成了可核查的规范要求。守护：无守护列的禁令条目MUST在豁免表在册，否则校验器红。

关于 "Everything is Workflow / Event / Tool"

原方案稿的这三条被降级：它们描述的是实现风格而非判断准则，且已被 FG-3（事件驱动）与 §39（工具面）覆盖。作为"原则"它们无法回答分歧——当有人问"这个检查该做成 Tool 还是校验器"，"Everything is Tool"给出的是错误答案（正解见 FINV-1）。保留一条无法裁决分歧的原则，会稀释其余原则的权威。

Chapter 5知识驱动软件工厂#

本章是全书的核心命题。前四章的问题与原则在此收束为一条结构主张。

5.1 命题

FINV-2工厂的核心资产是 Knowledge，不是 Agent。Knowledge → Workflow → Agent → Code 是单向依赖链：上游MUST NOT依赖下游。Agent MUST被建模为知识的执行者，而非知识的产生者或持有者。

5.2 单向依赖链的四段

层是什么可替换性失去它的后果
Knowledge元语文件：项目的表、状态机、决策、边界、部署事实不可替换（FP-3）工厂失去全部价值；智能体退回猜测
Workflow确定性编排：什么事件触发什么活动、什么闸门必须通过可替换（换编排引擎）失去可重放性与可预测性，但知识仍在

Code产物—可从上游重新生成

把 Agent 放在第三位有三个直接后果，它们解释了本规范后文的大部分约束：

  1. Agent 无状态化　Agent 不"记住"项目——它每次从元语重新加载。这消除了"不同 agent 记忆不同"这一类上下文不一致（PS-1），代价是每次会话的加载成本，用切片读取缓解（§16.5）。
  2. 知识改进优先于模型改进　产出质量不佳时，第一诊断对象是元语的完整性与准确性，不是 prompt 或模型。§25.7 的度量体系据此设计。
  3. Agent 数量不是能力指标　增加 agent 不增加工厂能力，只增加并行度与协调成本。能力的增长来自知识覆盖面的增长。

5.3 与 Kubernetes 声明式模型的类比与差异

结构同构：元语是期望态，代码是实际态，校验器是控制器。关键差异在差异处置——Kubernetes 控制器自动把实际态拉向期望态；ASFAS 校验器只报告差异，绝不自动收敛（FP-5）。

原因是两者的"差异"含义不同。Pod 数量不符只有一种解释（需要调谐）；而元语与代码不符有两种解释：文档过时了，或者代码写错了。自动收敛必须先假定其中一方正确，而这个假定无法由机器做出。

FR-4元语与代码不一致时，实现MUST停止并报告冲突，MUST NOT单方面修改任意一侧。项目SHOULD维护一张已知有意偏离表，登记那些"结论未变、实现已改主意"的条目。

Evidence · 为什么需要"有意偏离表"

参考实现的登记册里有一条决策写着采用某队列库，而代码实际用了另一种实现——这是实施时有意改的主意，不是 bug。没有这张表，下一个智能体会自作主张把代码"修正"回登记册写的方案。 偏离表的作用不是记录债务，是阻止基于登记册的错误修复。同理，项目SHOULD维护"已知松弛点"表，标注那些故意保留的不一致，避免被顺手"修好"。

5.4 与 Temporal 的类比与差异

Temporal 用事件历史的确定性重放来恢复工作流状态，要求活动是幂等的、工作流代码是确定性的。ASFAS 借用这个结构，但重放对象不同：

TemporalASFAS
重放什么工作流事件历史工作流事件历史 + agent run 血缘
确定性来自工作流代码不含非确定操作编排层确定性；agent 活动本身非确定
重放目的恢复执行恢复执行 + 事后审计归属（PS-4）
非确定性处置禁止隔离在活动内；活动输出须经确定性闸门验证

这条差异决定了 §41 工作流模型的一个核心约束：模型的非确定性可以存在，但只能存在于活动内部；活动之间的推进条件必须是确定性的。否则整条工作流不可重放，PS-4 无解。

5.5 这套体系不适用的场景

诚实地划出边界（FP-7）。以下场景采用 ASFAS 的成本高于收益：

场景为什么不适用

单人 + 单会话 + 短周期上下文不一致的前提是"多个持有者"。人脑里那份就够用
代码即完整规格的项目如纯算法库：没有状态机、没有跨模块约束、没有部署事实，元语无内容可写
需求本身高频剧变的探索期元语会成为变更摩擦。SHOULD等结构稳定后再引入，先只立 DECISIONS.md

8.2 为什么是六本，不是三本或十本

这是本规范被问得最多的问题。答案不是"经验上差不多够"，而是一条正交性判据：

FR-7元语集合MUST满足正交性：每本回答一类问题，且任两本回答的问题类不重叠。新增一本元语的充分必要条件是——存在一类项目事实，它无法放进现有任何一本而不制造重叠。仅因某本"太长"而拆分MUST NOT构成新增理由（应改为分小节切片，见 §16.5）。

六本核心元语沿三条正交轴划分：

8.3 AGENTS.md 为什么不是元语

原方案稿把 AGENTS.md 列为"六个知识文件"之一。本规范更正这一点，理由是结构性的：

FR-8AGENTS.md MUST是入口指针而非元语：它MUST NOT含任何一手事实，只含 ① 指向六本元语的指针与一句话职责，② 改哪类代码前必读哪本的阅读规则，③ 硬规矩与禁止行为，④ 命令清单。任何在 AGENTS.md 中出现的一手事实MUST视为 FP-1 违反。

如果 AGENTS.md 是元语，它必然复制其他六本的内容（否则它写什么？），而复制即制造第二事实来源。它是目录，不是章节。这个区分有实际后果：

  • AGENTS.md SHOULD保持在 100 行以内——它是被每次加载的文件，而六本元语是按需切片加载的。
  • AGENTS.md MUST NOT写具体数字（模块数量、文件行数）。写数字的文档注定漂移——改为写"以 ls 为准"或写结构描述。
  • 它的校验器检查的是指针可解析性，不是内容正确性。
Evidence · 数字漂移

参考实现的 AGENTS.md 曾声称某目录有 19 个模块（实为 21），前端为"43 行骨架"（实为多个页面 + UI 原语）。两处都在补元语时被查出。修法不是把数字改对，而是删掉数字——因为改对的数字下个月还会错。

8.4 项目层的非目标

FR-9项目的元语MUST只写事实，MUST NOT写愿望。DOMAIN.md 写 schema 现在的样子，不是应该的样子；"应该的样子"MUST进 DECISIONS.md 的未决段或需求文档。

这条约束容易被低估。混入愿望的元语无法对拍——校验器会持续报红，团队于是给它加豁免，最终豁免表比契约表还长。事实与愿望的分离，是元语可校验的前提。

决策理由
#理由反驳过的替代方案
1自研运行时是纯成本：它不属于核心资产（FP-3 明确运行时可替换），投入自研等于在可替换层投重资自研 —— 已否决
2SDK 原生提供本体系必需的四项机制：SubAgent、Session 持久化、MCP 工具面、流式与计量裸 API + 自建循环 —— 需重建这四项
3MCP 工具面提供可审计的收窄接口：agent 能做什么由 server 暴露什么决定，比在 prompt 里写"请不要改迁移"可靠一个量级prompt 约束 —— 不可验证
4参考实现的技术栈为 Node/TS，与 SDK 一致，无跨语言桥接成本Python 编排框架 —— 引入进程边界
为什么不用通用 Agent 框架（含 OpenClaw 类）

这类框架的设计目标是让 agent 能做更多事；本体系的设计目标是让 agent 只能做被授权的事。两者在三处直接冲突：

失败处置自主重试直到成功超护栏MUST升级给人，不静默重试（§27）
决策位置agent 自主判断下一步推进条件由确定性工作流裁决（FG-3）

这不是"那些框架不好"，而是它们优化的方向与本体系相反。在受监管场景下，开放的工具面是需要被抵消的属性，而不是卖点。

12.2 为什么 FR-13 排除了"工厂自动更新元语"

一个诱人的想法是：既然校验器能发现元语与代码不一致，为什么不让工厂自动把元语改对？

这在 §5.3 已从"差异有两种解释"角度否决过。此处补一个更强的理由：如果工厂能写元语，元语就不再是期望态，而变成实际态的镜像。它会自动收敛到"代码现在是什么样"，从而永远为真、永远无法报错——校验器变成恒绿。

这是一种假绿（PS-3）

自动同步的文档是最隐蔽的假绿：它看起来是最高级的自动化，实际上销毁了闸门的全部价值。元语的价值恰恰来自它可能与代码不符——那个不符就是信号。

Chapter 15元语模型总论#

15.1 定义与判据

MS-1一份文档要成为元语，MUST同时满足五条判据：①单一类别——只承载一类项目事实；②权威——该类事实在此处是唯一权威定义，他处只可引用；③可解析——规范性内容以结构化片段（表格 / 代码块）承载，非自然语言散文；④可对拍——存在代码或环境侧的闭集与之做集合相等比较；⑤有闸门——对拍失败时默认测试命令报红。

五条缺一不可，且每条都排除了一类常见的伪元语：

缺哪条退化成失效方式
缺 ① 单一类别大杂烩文档无法确定改某类事实时该读哪本；智能体只能全文加载
缺 ② 权威摘要 / 缓存与真正的权威处分叉，成为假事实（PS-2）
缺 ③ 可解析设计说明书校验器写不出来；只能靠人工 review，而人写文档必然漏
缺 ④ 可对拍愿望清单永远无法判定它是否为真（FR-9）
缺 ⑤ 有闸门君子协定违反无成本，几个月后无人遵守
判据 ④ 为什么要"集合相等"而不是"子集"

子集检查只能发现"代码里有文档没登记"，发现不了"文档登记了代码里没有"——后者是死条目，同样是假事实。智能体读到一个不存在的表名会基于它写代码。因此对拍MUST双向：缺项与死项都报红。

15.2 元语全集

元语集合是分层的：六本核心元语对所有项目必需；两本条件元语在触发条件满足时必需；AGENTS.md 是入口指针而非元语（FR-8）。

15.3 条件元语的触发条件

MS-2条件元语的存在性MUST由客观触发条件决定，MUST NOT凭偏好取舍。触发条件满足而元语缺失 = 不符合；触发条件不满足而元语存在 = 违反 FP-6（预埋）。

条件元语触发条件治理对象不满足时

AGENT-OPS.md仓库代码由 coding agent 参与编写写这个仓库的 agent：动作分级、禁令、血缘、护栏MUST NOT创建

MS-3AI.md 与 AGENT-OPS.md MUST NOT合并。二者的治理对象、读者、生命周期与违规后果完全不同：前者约束产品向用户承诺什么，后者约束开发过程如何被信任。一个项目MAY只有其中一本、两本都有，或两本都无。

这条看似琐碎，实际防的是一类真实混淆。参考实现 GMPGCPwork 的产品侧没有 AI 能力（它是文档协作平台），但仓库由 coding agent 编写——因此它有 AGENT-OPS.md 而刻意不设 AI.md，并在文档中明确声明"将来若产品引入模型生成面，另立一本，不要往本文件里塞"。而 diabetes 的情况相反。把两者合并会让任一项目的元语同时包含无关内容与缺失内容。

15.5 元语间的引用关系

MS-5元语引用图MUST无环。结论MUST单向汇聚到 DECISIONS.md（ID + 一句话 + 结论 + 出处），论证MUST留在出处元语。所有跨元语引用MUST是可解析的相对路径链接；链接目标不存在 = 红。

无环性不是洁癖。有环的引用图意味着存在"A 说见 B，B 说见 A"的情况——智能体会在两者间循环，而人会放弃阅读。DECISIONS.md 作为汇聚点是唯一被允许被所有元语引用的元语，因为它只含指针不含论证，不会产生回指需求。

15.6 元语不是什么

16.3 契约段与叙述段的分界

这个区分是元语设计中最有实用价值的一条，因为它直接映射到智能体的写权限：

MS-7元语MUST可区分契约段与叙述段。契约段MUST被校验器解析，改动MUST归入高影响动作等级（须人工放行）。叙述段MUST NOT被解析，改动MAY归入低影响等级（智能体自主 + 事后审计）。

契约段叙述段

16.4 格式契约附录

MS-8每本元语MUST在末尾附格式契约，逐条写明校验器的解析规则（哪张表的哪一列被解析、ID 是否需反引号包裹、代码块的字段顺序等），并MUST包含一条兜底规则：任一解析目标解析为 0 行 = 格式契约破坏 = 红。

16.6 松弛点表

MS-10存在故意保留的不一致时，元语SHOULD设"已知松弛点"表，逐条登记：不一致内容 · 为什么保留 · 什么条件下收敛。未登记的不一致MUST视为漂移。

松弛点表的作用不是记录技术债，而是阻止错误修复。参考实现的 DOMAIN.md 登记了六处故意的松弛（未收敛的枚举、类型偏弱的列、两处缺外键、一张已跑过迁移的死表、未实现的乐观锁）。文档里明确写着"那些不是 bug，别顺手修"。

Evidence · 三张"防止错误修复"的表

本规范要求的三张表都不是记债务，而是防止下一个智能体做出看起来正确的错误改动：DOMAIN 的松弛点表防止顺手"修"故意的不一致；DECISIONS 的有意偏离表防止把代码"修正"回登记册写的旧方案；AGENT-OPS 的豁免表防止误以为某条禁令有机器守护。三者共同解决同一个问题：智能体缺少"这是有意的"这一类信息，而代码本身无法表达意图。

16.7 版本管理

MS-11元语MUST NOT维护独立版本号。元语的版本MUST是其所在提交的版本——元语与代码MUST在同一提交内保持一致。语义引用中的 @version（§13.3）MUST解析为提交标识，而非文档内自述的版本号。

理由与 FR-8 禁止写数字同源：文档内自述的版本号是又一个会漂移的数字。而提交标识天然准确、天然可对拍、天然可回放。

MS-12以下三类改动MUST在同一提交内完成，MUST NOT分次提交：① 契约段改动 + 对应代码改动；② 新增决策入册 + 在出处补论证；③ 未决项决出后入册 + 从未决段销项。

MS-12 是"文档不可能过时"的操作化形式。允许分次提交就等于允许存在一个"文档已改代码未改"的中间提交——而那个提交会被智能体读到。

Chapter 20FLOWS.md#

20.1 职责与边界

FLOWS.md 描述动态事实：每台状态机的状态集合、转移、触发入口、触发者、受约束的不变量、以及是否已实现。它是本规范中信息密度最高的元语——参考实现的经验是这本查出的问题最多。

MS-23凡有状态字段的数据对象都MUST登记一台状态机，不得只登记"主要的几条"。漏登记一台等于给智能体留一片无契约区，而它会在那片区域自由发挥。

20.2 flow 块格式

machine: <对象>.<状态字段>
enum:    <枚举名>
states:  [<全部取值，须与 DOMAIN 一致>]
initial: <插入时的初值>
- <from> → <to> | via: <入口> | by: <触发者> | inv: <INV-n 或 -> | impl: yes|no

MS-24每条转移行MUST五段齐全：from → to · via（入口：路由或调度器符号）· by（谁能触发）· inv（受哪条不变量约束，无则 -）· impl（是否已实现）。缺任一段MUST报红——不允许"以后补"。

段为什么必需缺了会怎样
via转移的唯一合法入口智能体在第二个地方也写一次状态转移，绕过守卫
by权限判断的依据无法判断某个角色调这个接口是否越权
inv改动时必须读哪条约束改到合规路径而不知道踩了哪条线
impl区分"待办"与"死值"把未实现的状态当作可依赖的行为

20.3 impl 是状态级语义，不是转移级

MS-25impl 的语义MUST是状态级：impl: yes 表示该目标态在代码中确有写入点；impl: no 表示该目标态没有任何写入点。校验器MUST显式检测同一目标态被同时声明 yes 与 no 的矛盾情形。

Evidence · 一次语义假绿

参考实现的校验器初版把 impl 当转移级语义。结果同一张表上 A→B (impl: no) 与 C→B (impl: yes) 互相矛盾却都判通过——因为逐条检查时两者各自"成立"。改成状态级语义并显式检测矛盾声明后才真正生效。

结论写进规范：语义没想清楚的校验器会给出虚假的绿。 这是 PS-3 的第一类，也是最难发现的一类——因为校验器确实在运行，确实在检查，只是检查的东西比它声称的粗。

            impl:no  的目标态  →  代码中须不存在写入点
            同一目标态被声明 yes 且 no  →  红

20.5 这本元语的发现密度为何最高

Evidence · 一次补全查出五类问题

参考实现补 FLOWS.md 时（14 台状态机 / 37 条已实现转移 / 22 条未实现），查出五类此前无人知道的问题：

  1. 指标无数据来源——某个状态字段没有任何代码写入，导致产品需求文档里列的一项成功指标根本做不出看板。
  2. 整台状态机零实现——某对象建出来后永远停在初始态，四个后续状态全是死值，进度统计无从统计。
  3. 生产环境不会发生的转移——依赖一个缺失的后台消费者，此前只存在于口头认知，现在被机器登记在册。
  4. 四个冗余枚举值建议删——各有具体理由（串行流程使中间态无观察价值、两步合并为一次同步调用等）。
  5. 接口响应的状态词汇与数据层枚举不同源——某接口返回一个数据层枚举中不存在的状态值，前端会误以为两者同源。

为什么密度最高：DOMAIN 对拍的是静态结构，而结构错了通常编译期就会暴露；FLOWS 对拍的是行为，而"某个状态没人写"这类缺陷不会让任何测试变红，只会让看板永远空着。行为层的缺失是沉默的，这正是需要机器登记的原因。

Chapter 21DECISIONS.md#

21.1 定位：登记册，不是论证书，也不是日志

MS-27DECISIONS.md MUST是登记册：每条决策占一行，含 ID + 一句话议题 + 结论 + 出处。论证MUST留在出处元语，MUST NOT复制进本册（FP-1）。本册MUST NOT组织为按时间排列的日志。

三种形态组织方式为什么本规范选登记册
论证书每条决策一页完整论证与出处元语重复 → 第二事实来源；且长到没人读
日志（ADR 目录）按时间编号，每条一文件，含"已被 ADR-N 取代"要回答"当前结论是什么"须遍历全部条目并推演取代链
登记册按命名空间分表，每条一行，只放当前结论一次查询即得当前结论；ID 可被代码引用并双向对拍

选登记册的决定性理由是可对拍。日志形态无法回答"代码里这个 ID 是否有效"，而登记册可以：代码里出现的 ID 必须在册，在册但零引用的给出警告。这让决策从文档变成可验证的约束。

21.2 命名空间表：必须放在最前面

MS-28DECISIONS.md MUST以命名空间表开篇，列出全部 ID 前缀、各自含义、论证出处、当前数量。命名空间MUST NOT在视觉上互相混淆（§18.4）。

为什么它必须在最前面：智能体拿到一个 ID（如 B-3）时，第一个问题是"这是哪类东西、该去哪查"。如果要读完全文才能推断，它会去错的地方查，查不到后自行推断含义。命名空间表把这一步从推断变成查表。

典型命名空间含义论证出处
不变量任何实现都不得违反的硬约束不变量清单 / 测试清单
架构决策工程层不可逆选择ARCHITECTURE.md
边界规矩模块/包之间的硬边界ARCHITECTURE.md
UI 反模式呈现层禁止事项DESIGN.md
业务/技术决策点需业务或架构拍板的选择需求 / 深度设计文档

21.3 三个必备特殊小节

① 未决项唯一位置

MS-29未决项MUST只存在于本册的一个小节。其他文档MAY指向它，MUST NOT各自维护未决清单。决出后MUST入册 + 销项，同一提交（MS-12 ③）。每条未决项MUST写明"决出前禁止做什么"。

"唯一位置"是对 MA-4 的正面回答。散落的未决清单会产生三种故障：同一问题被反复讨论；已决的项在另一处仍显示未决；智能体基于过期的"未决"状态选择保守实现。

② 决策 ↔ 实现的已知偏离

MS-30在册结论与代码现状不一致时，本册MUST设"已知偏离"小节登记事实：ID · 在册结论 · 代码现状 · 性质（已改主意 / 未实现 / 部分实现）。MUST NOT在此小节修改决策结论——改结论须走重新拍板。

Evidence · 这张表的唯一目的

参考实现登记了六处偏离，最典型的一条：登记册写着采用某队列库，代码实际用了另一种实现——这是实施时有意改的主意。文档里直接写明这张表的价值：智能体看到登记册与代码不一致时，不会自作主张去"修正"代码。

注意"性质"列的必要性：已改主意 意味着代码是对的、登记册待更新；未实现 意味着登记册是对的、代码待补。两者的修复方向完全相反，不标注性质等于不提供有效信息。

③ 格式契约附录

见 MS-8。本册的特殊之处：ID MUST用反引号包裹（使 grep 可区分 ID 与普通文本），且子编号（如 INV-3.2）MUST按父编号查册。

22.4 环境事实的特殊价值

DEPLOY.md 是唯一能记录"环境的坑"的元语，而这类坑造成的时间损耗通常最大——因为它们的症状与真实原因无关。

Evidence · 症状与原因无关的一类故障

参考实现记录了一个反复浪费时间的假象：容器编排把数据库端口绑到通配地址，而主机上的同类服务绑了更具体的回环地址；连接回环地址时主机那个实例赢。于是现象是"明明起了容器，却报数据库角色不存在"——报错实际来自主机实例。

这类事实只能写在元语里：代码里看不出来，编排文件里看不出来，只有把"实际发生了什么"记录下来才能阻止下一个人（或智能体）重新踩一遍。这也是 DEPLOY.md 的"本地依赖事实"小节存在的理由。

读否定分支合规路径的改动，必须逐条读守卫判据的否定分支一处守卫从 !perm || 改为 perm &&，顺序未变但 fail-closed 变 fail-open（§4 FP-4）
为什么"先判归属"值得写成硬规矩

它对应一个智能体特有的失效模式：智能体默认自己是唯一变量——看到红就假设是自己改坏的，于是开始修一个它没有造成的问题。人类工程师有"这个测试一直是红的"这类背景知识，智能体没有。缺少的不是能力，是历史，而历史只能由元语或流程提供。

23.4 豁免表：诚实的机器化

MS-39无机器守护的约束MUST在豁免表在册，含：约束 id · 为什么无法机器化 · 失效条件（什么情况下这条豁免不再需要）。校验器MUST检测"禁令表中标记为无守护但未在豁免表在册"的条目并报红。

这是把 FP-7（诚实缺口）从美德变成可执行检查的具体机制：你可以有挡不住的规则，但你不能不承认它挡不住。校验器不检查规则是否被遵守（它做不到），而是检查你是否诚实地登记了它做不到。

Evidence · 两条在册的诚实缺口

参考实现的豁免表登记了两条：① 某条禁令（agent 自行推送）无机器守护，因为本地凭据层面无法区分执行者；② 护栏阈值无运行时强制点，因为尚无编排面，只能事后从血缘记录看出越界。

文档里直接写着理由：登记一条挡不住的禁令，比假装它被挡住要好——读者由此知道该靠人盯，而不是误以为有闸门。

Chapter 25校验器契约与漂移经济学#

元语的价值全部依赖校验器。本章定义校验器本身的规范——因为一个写错的校验器比没有校验器更危险（PS-3）。

25.1 校验器的七条契约

VC-1确定性　校验器MUST是确定性程序，MUST NOT调用模型。相同输入MUST产生相同输出（FINV-1）。

VC-2只诊断　MUST NOT提供 --fix。传入修复类参数MUST以非零码退出并说明理由（FP-5）。

VC-3格式先验　MUST先校验格式契约再校验内容。任一解析目标解析为 0 行MUST判为失败，MUST NOT判为"无违规"（MS-8）。

VC-4双向　对拍MUST双向：文档缺项与文档死项均报红。单向子集检查MUST NOT计为对拍。

VC-5面向工作区　MUST检查即将提交的内容（工作区 + 暂存区），MUST NOT只检查已提交历史（FINV-6）。

VC-6扫描面显式　MUST在代码中显式声明扫描面，并SHOULD在元语的格式契约附录中登记，使扫描面的完整性可被审查（MS-33）。

VC-7负向验证　MUST随附负向验证记录：构造应失败的输入 → 确认失败 → 回滚 → 确认通过。未经负向验证的校验器MUST NOT计入一致性证据（FR-3）。

25.3 负向验证协议

VC-8负向验证MUST覆盖每一条检查维度，而非每个校验器一次。一个含五条检查维度的校验器MUST有五组负向验证。

对每条检查维度 d:
  1. 在工作区注入违反 d 的最小改动
  2. 运行默认测试命令  →  MUST 红，且错误消息 MUST 指出 d 与位置
  3. 回滚改动
  4. 再次运行           →  MUST 绿
  5. 记录：维度 · 注入内容 · 观察到的消息

第 2 步的"错误消息须指出位置"不是附加要求。一个报红但不说哪里错的校验器，会让智能体开始随机试探——它会改一处、跑一次、再改一处，最终可能通过修改元语来消除报错，恰好绕过了对拍的意义。

25.4 扫描面的完整性

扫描面缺陷是最长寿的一类缺陷，因为它无症状（§22.2）。本规范要求两条对策：

对策做法能发现什么
显式声明扫描面写成常量数组而非散落的 glob审查时能一眼看全
反向枚举SHOULD额外做一次全仓扫描，把命中但不在扫描面内的位置列为警告"有个地方在读 env 但不在我的检查范围内"

反向枚举是把"我不知道我不知道什么"变成"我知道有个地方我没查"。它的输出是警告而非失败——因为可能确实有合法的例外——但它让例外浮出水面。

25.5 闸门位置：反馈延迟是漂移的主因

VC-9全部校验器MUST挂进项目的默认测试命令，而不只是 CI 的独立任务。CI SHOULD保留独立任务作双保险。校验器SHOULD在测试套件之前执行——它通常是秒级的，先跑能让快速失败更快。

理由是行为经济学而非工程洁癖：智能体在本地跑测试时就该看到治理红，而不是提交后等 CI 才知道。反馈延迟是无人值守场景下漂移累积的主因——延迟越长，被发现时已经叠加的错误改动越多。

FINV-8承载闸门的命令MUST NOT长期处于失败状态。已知的、先于当前工作存在的失败MUST被隔离（修复、跳过并给出明确消息、或显式登记为已知失败清单）。

为什么这条是不变量

闸门挂进一个长期红的命令等于没挂——智能体（和人）会学到"红是常态"，然后停止阅读错误消息。这与"摆设规则"是同一种病：规则存在但无人执行，且它的存在还提供了虚假的安全感。

参考实现在闸门内移后立刻遇到这个问题：目标命令在当时的提交上本来就是红的（三个先于该工作存在的原因）。处置方式是逐条定位、修掉可修的、给不可修的加明确的跳过消息——而不是接受"红是常态"。

25.6 无法机器化时的规范做法

有些约束确实无法机器守护。本规范不要求假装能守住，而要求诚实地处理：

1. 判断是否真的无法机器化 —— 多数“无法”其实是“扫描面不够”或“语义没想清楚”
2. 若确实无法：
   a. 在禁令/规矩表的“机器守护”列显式写明「仅文档约束」+ 一句话原因
   b. 在豁免表在册：约束 id · 无法机器化的原因 · 失效条件
   c. 校验器检测「标记无守护但未在豁免表在册」→ 红          【MS-39】
3. 失效条件成立时（如启用了某项基础设施能力）→ 补守护 + 销豁免，同一提交

第 1 步值得强调。本规范收集的三次假绿中，没有一次是真的无法机器化——两次是扫描面/时点问题，一次是语义粒度问题。"这个没法自动检查"应当被默认怀疑。

Chapter 26智能体模型与生命周期#

26.1 智能体的定义

AG-1本规范中的智能体是一个四元组：(角色, 知识切片, 工具面, 动作等级上限)。四项MUST全部在能力注册表在册（MS-37）。MUST NOT存在"临时提升权限"或"运行时扩展工具面"的机制。

把工具面与动作等级写进定义，而不是作为运行时参数，是本规范与通用 agent 框架的关键差异（§10.2）。一个智能体能做什么在它被创建之前就已确定并可审计。

26.2 生命周期

AG-2Record 阶段MUST无条件执行，包括会话失败、超护栏中止、人工取消的情形。只记录成功会话的血缘是有偏采样，会使幻觉率与成功率指标失去意义。

26.3 无状态原则

AG-3智能体MUST NOT跨会话持有项目知识。每次实例化MUST从元语重新加载。跨会话可携带的只有：任务状态（typed，§13.3）、血缘引用、以及运行时的 checkpoint（§38）。

"Agent Memory" 在本规范中不是知识存储。它只允许存放两类内容：① 指向元语的语义引用；② 本次任务的中间状态。把项目事实存进 agent memory 会立刻重建 PS-1——不同智能体的 memory 会分叉，而分叉不可检测。

27.3 L3 禁令的判据

AG-6一条约束归入 L3 的充分必要条件是：即使有人批准，该动作本身仍然违规，或造成不可逆的证据损坏。满足此判据的MUST NOT提供放行路径；不满足的MUST NOT放进 L3（应归 L2）。

判据的实际作用：把流程偏好赶出 L3

参考实现最初把"不在主分支直接提交"写为禁令，后来发现它与该仓库全部历史矛盾——这是一条无人遵守的摆设规则。按 AG-6 重判：直推主分支是流程偏好，不是"放行也不合规"的动作，因此归 L2（须人放行）而非 L3。

摆设规则的危害与假绿同构：它存在、被写进文档、但从不生效，同时让人以为该风险已被覆盖。AG-6 的价值在于提供一个能把它们识别出来的判据。

典型 L3 禁令为什么放行也不行
修改已应用的数据迁移迁移历史是"系统曾是什么样"的证据；改它等于伪造历史。修 bug 只能出新迁移
削弱审计不可删守护直接违反产品对客户与检查方的核心承诺
给不变量测试加跳过标记或删断言让守护形同虚设却仍显示绿——假绿比没测试更危险

27.6 归级算法

动作等级MUST可由机器判定（AG-4）。判定过程本身是确定性规则，MUST NOT交给模型（FINV-1）。

输入：本次改动触及的路径集合 P
输出：最高动作等级 L ∈ {L0, L1, L2, L3}

for p in P:
  M ← 分级表中所有能匹配 p 的路径面
  if M 含 L3 面        →  返回 L3（短路，不再看其余路径）
  if M 为空            →  level(p) = L2      ← fail-closed（FP-4）
  else                 →  level(p) = 最具体那条的等级
L = max(level(p) for p in P)

AG-14未被任何路径面匹配的路径MUST归为 L2（须人工放行），MUST NOT归为 L0/L1。理由是 FP-4 的直接应用：分级表解析不出结论时拒绝，而不是放行。新增目录若忘了登记，后果是"多要一次放行"而非"未经授权就改了合规代码"。

AG-15路径面冲突时MUST取最具体的匹配（字面段最多者优先；同具体度取更高等级）。L3 匹配MUST短路——一次改动只要触及任一 L3 面即整体判为 L3，MUST NOT因其余路径等级较低而稀释。

场景匹配判定依据
只改前端页面L1 面L1—
改前端页面 + 契约层L1 + L2L2取 max
改元语的叙述段L1 面（元语非契约段）L1MS-7 契约段/叙述段分界
改元语的契约表格L2 面L2同上
新建的未登记目录无匹配L2AG-14 fail-closed
改一行前端 + 碰了已应用迁移L1 + L3L3（拦截）AG-15 短路
为什么"同具体度取更高等级"

两条同样具体的规则同时命中，说明分级表本身有歧义。此时取更高等级不是最优解，是安全解——它会多要一次放行，同时让歧义暴露出来（放行人会问"这为什么要放行"）。取更低等级则会静默地放过一个本该被拦的改动，且没有任何人会注意到。

28.5 任务拆分的粒度判据

AG-18一个任务是原子的，当且仅当它满足三条：① 能独立通过全部闸门（不依赖尚未完成的兄弟任务）；② 触及的路径面归级后是单一等级；③ 声明的不变量集合自洽（不需要另一任务同时改动才成立）。不满足任一条MUST继续拆分或合并。

违反后果
违反 ①产生"暂时红"的中间提交，违反 FINV-8；后续智能体读到自相矛盾的仓库
违反 ②整个任务被归为最高等级，低风险部分被迫等待放行；或诱导拆出"不含 L2 的那部分"先提交，制造半成品
违反 ③血缘的 declares 无法真实——声明的不变量在本任务范围内根本无法被满足，直接产生幻觉率

判据 ① 同时给出了拆分的下界：不能拆到"改一个函数签名"这种无法独立过闸门的粒度。本规范不给拆分的上界——上界由护栏（AG-10）间接施加：拆得太粗会反复超迭代上限。

28.6 失败重派

AG-19失败重派MUST NOT改动任务的验收条件：不得放宽断言、不得缩小声明的不变量集合、不得下调等级上限。允许改动的只有给 Worker 的提示信息（如附上失败位置、指出该读哪个知识切片）。

AG-20同一任务连续重派MUST NOT切换到更宽松的角色或更高等级的执行者以求通过。达到重试上限MUST升级给人（WF-11），MUST NOT自行"换个更强的模型再试"——反复失败通常是任务定义或知识缺口的信号，不是执行能力的信号。

这两条封堵的是同一个滑坡

AG-19 与 AG-20 合起来，堵死了 Supervisor 让任务"看起来成功"的全部途径：不能改验收条件，不能换执行者，不能静默重试。剩下的唯一出路是升级给人。

这与 FINV-10（重构 = 断言零变更）、WF-11（禁静默重试）指向同一件事：在一个以成功率为指标的系统里，必须提前堵死所有伪造成功的路径，否则指标会先于能力被优化。

29.3 不变量声明的推导规则

步动作性质

2取任务涉及的状态转移，查 FLOWS 对应 flow 块的 inv: 段确定性（查表）
3并集去重，得候选集确定性
4从候选集中剔除本任务确实不触及的项，逐条给理由非确定（Spec 判断）

AG-23declares MUST是步骤 1–3 所得候选集的子集。Spec MUST NOT凭判断添加候选集之外的不变量——若确有遗漏，说明 DOMAIN/FLOWS 的不变量落点标注不全，MUST先修元语（L2，须放行）而非在任务卡里绕过。

这条把"声明不变量"从自由判断收窄成只减不加的过滤，理由有二：候选集来自元语查表，可复现；而"这个改动还会影响某条不变量"的判断若允许凭空添加，就无法与幻觉区分。同时它制造了一条反向压力——元语标注不全会立刻在任务卡阶段暴露，而不是等到审计时。

Chapter 34禁止智能体化的面#

本章是 FINV-1 的操作化清单。它规定哪些能力MUST NOT被实现为智能体。

AG-13以下面MUST NOT实现为智能体，MUST保持确定性实现：① 元语校验器；② 类型检查与静态检查；③ 迁移生成；④ 不变量的运行时校验（如互斥关系、唯一性、哈希链）；⑤ 动作等级的归级判定；⑥ 预算与迭代护栏的计数。

34.1 判据

问题是 → 禁止智能体化
该判断能否写成规则（含查表、集合运算、模式匹配）？能 → 禁止
相同输入是否必须产生相同输出？是 → 禁止
该判断的错误是否会导致假绿？是 → 禁止（模型的错误不可复现，无法回归）
该判断是否构成合规证据？是 → 禁止（不可验证的证据不是证据）

34.2 为什么这条必须是不变量

把确定性检查做成智能体，会同时失去三样东西：可复现性（同一输入两次结果可能不同）、可验证性（无法对检查器本身做负向验证）、可解释性（无法回答"为什么这次判通过"）。而这三样恰好是整个一致性体系的地基。

一个诱人但错误的方向

"让一个 Reviewer Agent 去检查文档与代码是否一致"听起来比写十三个校验器省事得多。但这样做的结果是：漂移检测本身变成了一个会产生幻觉的过程——它可能报告不存在的漂移，也可能漏掉真实的漂移，且两种错误都无法被系统地发现。校验器可以被负向验证，模型判断不能。

41.4 闸门的顺序规则

WF-3同一阶段存在多个闸门时，顺序MUST为：确定性闸门 → Reviewer 闸门 → 人工放行。确定性闸门MUST NOT排在模型判断之后——让模型去审查一个连类型检查都没过的改动是纯粹的浪费，且会产生关于"它本来就不该存在的代码"的意见。

Chapter 46重构工作流#

46.1 判据先于流程

FINV-10重构的定义是行为不变。因此重构的验收条件MUST是：全部闸门通过，且测试断言集合零变更。修改、删除或放宽了任一断言的改动MUST NOT被称为重构，MUST转入需求开发或缺陷修复工作流。

把它定为不变量而非规则，是因为它同时封堵了 §41.8 指出的最危险失败模式：智能体在反复失败后修改验收条件使闸门通过。"这是重构，测试要跟着调整"是这类改动最常见的说辞。断言零变更这一条把说辞变成可机器判定的事实。
